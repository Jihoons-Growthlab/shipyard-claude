# 구현 인덱스

요구사항 원문은 각 명세에만 있다. 이 파일은 순서와 공통 판단 기준만 담는다.

## 환경 점검 (최초 1회)

`node -v`, `npm -v`, `uv --version`, Google Chrome 설치 여부를 확인하고 결과를 `PROGRESS.md`에 남긴다. Unity 점검은 단계 11에서 한다.

명세는 `specs/` 아래 파일이다(`foundation.md`, `F01.md` 등). 단계 3부터 공통 스타일은 `ui.md`를 재사용한다.

앞 단계에서 뒤 단계가 필요한 경우:

- 단계 3: 아직 없는 화면은 제목과 조회 전용 배지만 있는 자리표시 화면으로 둔다.
- 단계 4: `3D 보기` 탭은 단계 11에서 추가한다.
- 단계 4~6: 도면 데이터가 필요한 동작은 시드로 테스트한다. 쓰기 API는 해당 단계에서 만든다.
- 단계 5: 패널의 도면번호 링크는 단계 7에서 도면 상세 모달에 연결한다.
- 단계 10: 도면 개정 영향의 도면 상세 모달을 재사용한다.

## 최종 수용 검증

1. 백엔드·프론트 전체 테스트와 프론트 빌드를 실행한다.
2. 시드 직후 값이 `foundation.md`의 기준 수치와 같은지 확인한다.
3. 계정별로 확인한다: admin(OTP), park.pm, lee.dwg, choi.qa(조회 전용), jung.new(승인 대기로 거절).
4. 브라우저 시나리오: 가입 → 승인 → 로그인 / 호선 등록·삭제 / 공정 추가·연계 / 실적 입력 → 상태 변화 / 도면 Rev 작성 → 결재 2단계 → 배포 → 공정 READY / 3D 탭.
5. 1440x900에서 각 화면을 이미지와 비교한다. 데이터 변경 시나리오는 임시 DB로 실행하고 끝나면 시드로 되돌린다.

## 기준의 우선순위

명세 > `reference/ui/` 이미지. 이미지의 데이터 값은 시드 기준 예시이며 하드코딩하지 않는다.

## 알려진 사항 (완성본 기준, 임의로 바꾸지 말 것)

- **실제 TOTP**: OTP는 RFC 6238이다. `123456` 같은 고정값은 없다. 시드의 demo secret은 데모 전용이다.
- **TOTP 등록 없음**: secret이 없는 사용자는 OTP를 켤 수 없다(409). QR 등록은 범위 밖이다.
- **날씨**: 실제 공급자가 없어 항상 샘플이다. LIVE로 표시하지 않는다. 가상의 공급자를 만들지 않는다.
- **PDF 샘플**: 파일 없는 리비전은 안내 박스만 표시한다. 가짜 PDF를 생성하지 않는다.
- **게이트 판정**: 과거 ISSUED 리비전이 있으면 최신이 DRAFT여도 통과한다.
- **실적 입력**: 도면 게이트를 검사하지 않고, 누적률 역행과 음수 공수도 허용한다.
- **시드 결재 일시**: 일부 `ActDt`가 기준일 이후다. 시드 그대로 둔다.
- **제외 범위**: 데이터 초기화 버튼, 이슈관리, 블록 독립 메뉴, 비밀번호 찾기, 이메일 인증, CAD 렌더링, 배포 서버 구성.

## 미확정·잔여 사항

- 호선 상세에서 조회 응답 전에 입력하면 늦은 응답이 값을 덮어쓴다. 새 구현에서는 조회 완료 전 폼을 비활성화해 해결한다.
- 데이터 서브탭 간 이동은 재조회로 작성 중 내용을 버린다(3D 탭 왕복은 유지). 완성본 동작을 유지한다.
- `POST /api/users/{emp_no}/reject`는 API만 있고 화면 버튼이 없다. 완성본과 같이 둔다.
- 1024px 폭에서 호선 목록은 패널 안에서 가로 스크롤된다. 페이지 전체는 넘치지 않는다.
- 호선 상태 자동 전이는 구현돼 있으나 완성본의 전용 수용 기록이 없다. 테스트를 추가해 확인한다.
- 프로덕션 정적 제공은 구현돼 있지 않다. 프론트는 Vite(dev/preview)로 실행한다.
- Unity 압축 빌드와 실제 배포 서버 헤더는 검증된 적 없다.
